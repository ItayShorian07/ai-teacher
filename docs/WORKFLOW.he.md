# שיטת העבודה של Limud

הפרויקט מפותח בידי בעל הפרויקט יחד עם סוכן קוד. עובדים בשינויים קטנים, בקוד קריא ועם בדיקות לפני שחרור. `main` מייצג קוד המיועד ל־production; כתובת נוספת לבדה אינה מבודדת נתונים.

## הסביבות

| סביבה | היכן הקוד רץ | נתונים ושירותים | מטרה |
| --- | --- | --- | --- |
| Development | המחשב המקומי, `npm run dev` | פרויקט Supabase לפיתוח ומפתחות בדיקה | כתיבה וניפוי תקלות |
| Preview | פריסת ענף ב־Vercel | אותו פרויקט פיתוח, ללא משתמשי production | בדיקות הרשמה וקבלה לפני מיזוג |
| Production | פריסת `main` ב־Vercel | פרויקט Supabase נפרד ומפתחות production | שימוש אמיתי |

יש שני פרויקטי Supabase, ובכל אחד מסד Postgres יחיד עם pgvector. אין צורך במסד וקטורי נוסף. Development ו־Preview יכולים לשתף נתוני בדיקה בשלב הנוכחי. אין בידוד נתונים בין ענפי Preview; בדיקות שמשנות schema נעשות בתיאום. אם יידרשו כמה שינויים מתנגשים במקביל, נוסיף בידוד לכל ענף.

לא מוסיפים כרגע ענף `develop` קבוע. לכל משימה יוצרים ענף קצר, למשל `feat/signup-flow`, `fix/auth-redirect` או `chore/environments`, ופותחים Pull Request אל `main`.

## מצב ההקמה

המאגר כולל בדיקות תצורה, כללי עבודה ו־CI. הגדרת הסביבות בשירותים אינה נוצרת מהקבצים האלה. לפני בדיקת הרשמה צריך להשלים את החיבורים הבאים:

1. לזהות איזה פרויקט Supabase מחובר לאתר הקיים ולהחליט שהוא פרויקט production. לא מסיקים זאת רק מכך שמפתח נמצא ב־`.env.local`. ליצור פרויקט פיתוח נפרד באותה ארכיטקטורה, לאחר בדיקת העלות בחשבון.
2. למלא ב־`config/environments.json` את `nonProductionSupabaseUrl` ואת `productionSupabaseUrl`. אלה כתובות ציבוריות, ללא מפתחות. `productionSiteUrl` מכיל את כתובת הפריסה המתועדת כיום ויש לעדכן אותו אם הדומיין משתנה. הערכים הריקים מכוונים: חיבור לשירותים ייחסם עד שיוגדר לאיזו סביבה הוא שייך.
3. לעדכן את `.env.local` במפתחות **של פרויקט הפיתוח בלבד**, עם `APP_ENV=development` ו־`NEXT_PUBLIC_SITE_URL=http://127.0.0.1:3000`. בהפעלה בפורט אחר לעדכן גם את הכתובת. לא לדרוס או להעתיק אוטומטית סודות קיימים. אפשר להריץ את הדמו בלי חיבורים באמצעות השארת כל משתני השירותים ריקים.
4. ב־Vercel לוודא שהפרויקט מחובר למאגר הנכון וש־Production Branch הוא `main`. ב־Preview להגדיר מפתחות פיתוח בלבד ו־`APP_ENV=preview`. ב־Production להגדיר מפתחות production ו־`APP_ENV=production`. אם מפעילים גם Vercel Development, להגדיר בו את ערכי הפיתוח. לא לסמן סודות production כמשותפים לכל הסביבות.
5. ב־Preview להשאיר את `NEXT_PUBLIC_SITE_URL` לא מוגדר. הקוד משתמש ב־`VERCEL_BRANCH_URL`, או ב־`VERCEL_URL` כשאין כתובת ענף. ב־Production להגדיר במפורש את הכתובת הרשומה ב־`productionSiteUrl`. לאחר שינוי משתני סביבה לבנות ולפרוס מחדש; ערכי `NEXT_PUBLIC_*` נקבעים בזמן build.
6. להחיל את `database/setup.sql` על פרויקט הפיתוח החדש בלבד, ולהגדיר בו SMTP, OTP, CAPTCHA ו־Google לפי הצורך. הגדרות Auth אינן מועתקות אוטומטית בין פרויקטים. לבדוק תחילה מה כבר הוחל בפרויקט production ולא להריץ שם bootstrap בעיוורון.
7. ב־Supabase של הפיתוח להגדיר redirect URLs ל־`http://127.0.0.1:3000/auth/callback`, ל־localhost אם משתמשים בו, ולכתובות Preview שבשליטת הפרויקט. בפרויקט production לאפשר את כתובת production בלבד. ב־Google OAuth להגדיר לכל פרויקט את callback של Supabase שלו. ב־Turnstile להשתמש ב־widget ומפתחות נפרדים לפיתוח ול־production, ולאפשר את ה־hostnames המתאימים. לא להשתמש במפתחות בדיקה ב־production.
8. ליצור מפתח Gemini נפרד לפיתוח, עם מגבלת שימוש מתאימה. לא להעתיק משתמשים או פרטים אישיים מ־production. להתחיל בשני חשבונות בדיקה ובחומר לימודי בדוי או מאושר.
9. ב־GitHub להגדיר הגנה על `main`: מיזוג דרך Pull Request, בדיקת `validate` נדרשת, חסימת force push ומחיקת הענף, והחלת הכללים גם על מנהל המאגר ככל שהמסלול מאפשר. כמפתח יחיד אין צורך לחייב אישור של אדם נוסף. קובץ ה־CI לבדו אינו מפעיל הגנה על ענפים.

`npm run check:env` בודק את תצורת ה־build שנקראת דרך Next.js. עבור סדר טעינת הקבצים של שרת הפיתוח: `npm run check:env -- --development`. בדיקה זו אינה מתחברת לספקים ואינה מוכיחה שהמפתחות, SMTP או CAPTCHA עובדים. `npm run check:connections` מבצע בדיקות קריאה מול הפרויקט שהוגדר, אחרי שבדיקת הסביבה עברה.

## מחזור עבודה לכל משימה

1. מגדירים תוצאה ברורה ותנאי קבלה קצרים. מחלקים משימה גדולה לשינויים שאפשר לבדוק בנפרד.
2. בודקים `git status` ועוברים לענף ייעודי לפני עריכה. לא פוגעים בשינויים קיימים. אם הענף כבר מכיל עבודה, מסיימים או מפרידים אותה לפני משימה חדשה.
3. מממשים את השינוי הפשוט ביותר שמתאים לארכיטקטורה הקיימת. קוראים את תיעוד Next.js המקומי לפני שינוי APIs או מוסכמות framework.
4. מריצים `npm run check`. מתקנים כשל לפני שממשיכים. שינוי התנהגות מקבל בדיקה ממוקדת כשיש סיכון ממשי; הרשאות, אימות, מכסות ובידוד סביבות דורשים בדיקות.
5. בודקים את ה־diff, יוצרים commit ברור, דוחפים את הענף ופותחים PR. הסוכן מבצע commit, push, מיזוג או פריסה רק כשהמשתמש מבקש את הפעולה. דחיפה עשויה להפעיל פריסת Preview אוטומטית.
6. בודקים ב־Preview את תנאי הקבלה עם נתוני בדיקה, ומתעדים ב־PR מה נבדק ומה לא. בעל הפרויקט עובר על התוצאה ועל הסיכונים הרלוונטיים.
7. לאחר שהבדיקות עברו, ממזגים ל־`main`. המיזוג מפעיל פריסת production כאשר חיבור Vercel מוגדר. בודקים שהפריסה הצליחה ואת הפעולה ששונתה. מוחקים את ענף המשימה לאחר המיזוג.

## רמת הקוד

- TypeScript במצב strict. שמות ברורים, פונקציות ממוקדות וזרימה שקל לעקוב אחריה. משתמשים בטיפוסים קיימים ונמנעים מ־`any` ומכפילויות כשאפשר.
- פורמט אחיד באמצעות Prettier ובדיקות סטטיות באמצעות ESLint ו־TypeScript. לא דוחסים קבצים לשורות ארוכות. לא מוסיפים שכבות או ספריות בלי צורך ברור.
- הערות קצרות באנגלית פשוטה, שמסבירות סיבה, מגבלה או החלטה. אין צורך לתאר פעולה שהקוד כבר מבטא בבירור.
- מאמתים קלט בגבול השרת. הרשאה וזהות נקבעות בשרת וב־RLS. מפתחות שרת אינם מיובאים ל־Client Components ואינם מקבלים קידומת `NEXT_PUBLIC_`.
- מטפלים בשגיאות באופן צפוי. לוגים אינם מכילים סודות, קודי OTP או פרטים אישיים של תלמידים. עיצוב קוד אינו תחליף לסקירת התנהגות ובדיקות.
- נמנעים משכתוב גורף שאינו נחוץ למשימה. משפרים את המודולים שנוגעים בהם ומפרידים שינוי ארכיטקטוני משמעותי ל־PR משלו.

## בדיקות ושחרור

`npm run check` מריץ פורמט, lint, בדיקת טיפוסים, בדיקות יחידה ו־build מבודד משירותים חיצוניים. בדיקות אלה אינן שולחות מיילים ואינן מפעילות Gemini. `npm run build` הרגיל בודק את התצורה האמיתית ולא עוקף הגדרות חסרות.

לפני שחרור שינוי בהרשמה בודקים ב־Preview: יצירת שני משתמשים, מייל OTP, קוד שגוי או פג תוקף, CAPTCHA, השלמת פרופיל, כניסה ויציאה, redirect לאותה סביבה, הפרדה בין פרופילים ומחיקת חשבון בדיקה. Google נבדק אם הופעל. אלה בדיקות קבלה שדורשות שירותים מחוברים; CI ללא סודות אינו מכסה אותן.

שינוי DB נוסף כקובץ SQL חדש וממוספר אחרי `005_username_login.sql`, עם הוראות הפעלה ובדיקה. הקבצים הקיימים הם בסיס ההקמה; לא משנים בדיעבד מיגרציה שהוחלה. מתעדים לכל סביבה אילו מיגרציות רצו. בהמשך ניתן להעביר את הרישום ל־Supabase CLI לאחר התאמת schema בפועל; אין כרגע פריסת DB אוטומטית.

מעדיפים שינויים תואמים לאחור: מוסיפים schema, מפרסמים קוד שמשתמש בו ורק בשחרור נפרד מסירים שדות ישנים. לפני שינוי production מכינים גיבוי זמין ובודקים את דרך השחזור. במקרה תקלה מחזירים פריסה תקינה קודמת ב־Vercel; rollback של האתר אינו מחזיר שינויי DB. מתקנים DB במיגרציה מתוכננת בהתאם לנתונים הקיימים.
